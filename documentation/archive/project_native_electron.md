Running sculptcore as a native C++ N-API addon in the Electron app (dual with the browser WASM path). Plan + live status: `documentation/plans/native-electron.md`. Test orchestration (CLI to build LiteMesh test scenes) is in [[project-electron-test-harness]] / `documentation/plans/native-electron-test-harness.md`.

**Done so far (2026-05-27):**
- Spike A.5: clang↔Electron N-API link de-risked. `sculptcore/spike/napi/` + `RESULTS.md`.
- Workstream A: `node make.mjs node [--smoke]` builds `build/native-node/sculptcore_node.node` for the Electron ABI; verified loading in Electron with `bindingCount()` → 103 registered descriptors.
- Workstream B slices B1+B2+B3 (`source/napi/napi_runtime.{h,cc}`): per-struct JS classes, member get/set at `ptr+offset`, `getBoundPointer`, `construct()` via default ctor, **method invocation** (`methodInvoker` marshals args+return via `MethodThunk`), and **bulk-data view** (`vectorView`/`vectorLength` over `litestl::util::Vector`). Verified in Electron: `CastRayIsect.t` round-trip, `Mesh.recalc_normals()`, `Vector<float,4>.resize(4)`→len 4 (arg marshalling)→Float32Array view reads zeros. **Key finding: Electron's V8 sandbox forbids external ArrayBuffers (`napi_no_external_buffers_allowed`) — no zero-copy; the view copies into a sandbox-internal buffer.** Class cache keyed by `buildFullName()` (all `Vector<T,N>` share bare name `litestl::util::Vector`). Deferred: Vector indexed get/set+iterator, strings, static methods, overload resolution, identity cache.

**Key decisions (non-obvious):**
- **Dropped node-addon-api; use raw C N-API (`node_api.h`).** Spike found node-addon-api's C++ `CallbackInfo::Length()` returns garbage under the repo's clang-on-Windows toolchain (reproduces at -O0 and -O3); the raw C ABI is correct. Only `cmake-js` was added as a dev dep.
- clang on Windows targets the MSVC ABI (under vcvars via `configureEnv.mjs`), so it links Electron's MSVC `node.lib`. cmake-js passes `/DELAYLOAD:NODE.EXE` in link.exe syntax → the clang++ driver rejects it; re-add via CMake `LINKER:/DELAYLOAD:node.exe` + `delayimp.lib`.
- The `sculptcore_node` MODULE target is in the root `CMakeLists.txt`, gated on `DEFINED CMAKE_JS_VERSION` (invisible to plain `make.mjs configure native`). Built into a separate `build/native-node/` dir (cmake-js's `/MT` CRT) so `build/native` is untouched. Entry: `source/napi/napi_entry.cc`.

- Workstream C (seam) + D (audit): gated opt-in native loader (`sculptcore/typescript/api/nativeBackend.ts`) + `loadWasm()` branch on `nativeBackendRequested()` (`globalThis.__SCULPTCORE_BACKEND==='native'`, set early in `entry_point.js` from `--backend`). Detects+reports native, falls back to WASM (non-breaking). De-numbering sites audited in `TODO.md`. Verified end-to-end via CDP: `--backend native` → `{backend:"native", addonBindings:103, wasmUp:true}`.
- Workstream C native factory free-functions: addon exports `meshCreateCube`/`meshBuildSpatialTree`/`spatialTreeFree` (call engine extern-"C" funcs, wrap returns as bound objects), plus `vectorGet`/`vectorLength`/`vectorView` for Vector iteration. Verified native pipeline in Electron: create cube → `mesh.v.capacity_`=4096 → `recalc_normals()` → build BVH → `tree.leaves()` (by-value Vector<SpatialNode*>) → vectorLength 2 → vectorGet(0) is a bound SpatialNode → free. So the native runtime drives the real engine (construct/members/methods/factories/Vector iteration).

- Also done: `vectorGet` (Vector indexed get) + fixed-size **Array member** support (`float3.vec` live per-index get/set into C++ memory, sandbox-proof — unblocks `float2/3` ring helpers). C++ runtime now covers construct/members/methods/factories/Vector-iteration/Array-members against the real engine.
- NativeManager TS assembly (`sculptcore/typescript/api/nativeManager.ts`): wraps the addon into the BindingManager surface — construct, getBoundVector (NativeBoundVector Proxy: length/index/iterator), Mesh_createCube/buildSpatialTree/free, float2/3 rings + `makeNativeInterface`.
- **App boots on native backend (milestone):** `loadWasm`'s `--backend native` branch returns the NativeManager-backed `IWasmInterface` (lazy gpu; heap fields absent). Verified via CDP: app boots (`hasScreen:true`, `sceneObjs:2`, zero renderer errors), `getWasm().__backend==='native'` (no WASM), wasm interface drives engine (cap 4096, leaves 2). Default sculptcore-free scene runs natively.
- **Array-element accessor bug — FIXED.** `obj.vec[i]` (fixed-size Array member, e.g. `float3.vec`) used to return a garbage first element (a denormal double = pointer reinterpreted as double). Root cause: the array wrapper was a plain object with `napi_define_properties` accessors (value-lifetime fragile under this clang/V8 sandbox). Fix: build it as a real `napi_define_class` instance — one cached class per (element-descriptor, length), index accessors on the **prototype** (like struct members, which never broke); per-instance base held by the wrapped `ArrayInstData`. Verified 0/3000 in-app over CDP. The boot-time-GC transient (first ring read after boot) is a SEPARATE lifetime watch-item tied to the deferred identity cache, NOT this bug.
- **GPU bulk-data path — done (2026-05-28):** addon exports `pointerBytes(boundObj, memberName, byteLen)` (reads a raw-pointer member e.g. `gpu::Buffer.data` off the descriptor → Uint8Array, external→copy fallback like vectorView; the void* never crosses to JS as a number) and `objectAddress(boundObj)` (C++ address as an opaque identity key). `gpuExecutor.ts` branches both seams: `bufferBytes` (HEAPU8 vs pointerBytes) + `bufferKey` (numeric `.ptr` vs objectAddress); WASM byte-identical (CDP-verified). Smoke test drives the real native pipeline `tree.update(gpu)` → 2 populated vertex buffers → correct-length real-data view + stable key. So native **GPUManager construction + buffer create/fill** works (per-frame loop calls createBuffer in C++, so JS string-arg marshalling isn't on the critical path). Also done earlier: extern-"C" `Mesh_free` (`mesh_shapes.cc`) → addon `meshFree`.

**Native litemesh scene runs end-to-end (2026-05-28).** `--backend native --gen-scene litemesh-cube` boots, builds the scene, pumps frames with zero console errors, and native `rayCast` matches WASM. Landed this session: `litemesh.ts rayCast` de-numbered (float3 ring, not HEAP poking; also fixed a hit-path leak); de-numbered BOTH batch executors (`api/gpuExecutor.ts` AND the visible one, `scripts/webgpu/batch.ts` — litemesh's viewport path is WebGPU via `drawQGPU`, NOT gpuExecutor) with `bufferKey`/`bufferBytes`/`vecMember` seams; addon `pointerBytes`/`objectAddress`; and **string member support** (`litestl::util::string` is a member-less `Struct("litestl::util::String")` → read `data_` char* at offset 0 as a JS string — needed because the WebGPU executor matches buffers↔shader-slots by name).

**✅ MILESTONE: native litemesh renders end-to-end (2026-05-28).** The litemesh cube renders in the app on the native backend (WebGPU path) — screenshot-verified (purple sphere at origin, identical to WASM; WASM re-verified, no regression). Full native pipeline proven: `Mesh_createCube` → `buildSpatialTree` → native `GPUManager.update` → draw batches → WebGPU `dispatch` reading native buffer bytes via `pointerBytes` → visible pixels. The last blocker was NOT a GPU validation error (error-scope probe was clean) — the WebGPU executor's native `bufferBytes` **threw** "pointerBytes missing" on the FIRST frame before the spatial tree fills its GPU buffers (`bytes===0`/null data → `pointerBytes` returns undefined → throw), and the throw aborted the whole `drawObjects` pass (caught + logged only as a warning → mesh AND overlay widget vanished). Fix: native `bufferBytes` returns an empty `Uint8Array` for a not-yet-filled buffer instead of throwing (both `scripts/webgpu/batch.ts` and `api/gpuExecutor.ts`). **Lesson: never throw on the bulk-data seam — match WASM's empty-view tolerance; the first frame races buffer fill.**

**✅ Native sculpt stroke renders end-to-end (2026-05-28).** A full sculpt dab runs natively on the litemesh (both backends drive the SAME stroke code; native-specific logic is contained in `NativeManager`). Verified in the live app: 12 DRAW dabs raise a ~0.9-unit bulge (native `rayCast` confirms; screenshot shows the bump), WASM re-verified no regression, typecheck steady at 106. Landed (sculptcore `2db9c36`, parent `9d3676a`):
- C++ runtime (`napi_runtime.cc`): factored arg marshalling into `marshalArg` + added the **Enum** case (execBrush's `SculptBrushes` arg crossed as nullptr before); **pointer+enum member set** in memberSetter (`exec.meshLog = meshLog`); `constructWith(structName, ctorName, ...args)` — named parameterized ctor with bound-object pointer args (`CommandExecutor "main"(SpatialTree*, Brush*)`); `makeNodeVector()` — empty owning `Vector<SpatialNode*>` for filterNodes' out-param, **recovering the specialization from `SpatialTree::leaves()`'s return descriptor** (it shares the bare `"litestl::util::Vector"` name → not lookup-able by element type).
- TS: `NativeManager.get / findVectorClass / constructWith` shims matching the `BindingManager` surface `sculptcore_ops.ts` uses; addon `constructWith`/`makeNodeVector` in `NativeAddon`. **Fix in shared `sculptcore_ops.ts`:** pass the bound Vector (`nodes`) to `execBrush`, not the `getBoundVector` inspection proxy (the proxy isn't napi-unwrappable; `nodes` works on both backends).
- **Gotcha:** a brush dab calls `freezeTopo()` (DRAW needs no live links); walking the tree again (`regenTreeBatch`/`tree.update`) before thawing crashes natively. The app thaws via `mesh.recalc_normals()` (auto-thaws) post-stroke. Also: re-`update`ing the tree with a *different* GPUManager doesn't refill buffers (tree isn't dirty for it) — reuse one manager.
