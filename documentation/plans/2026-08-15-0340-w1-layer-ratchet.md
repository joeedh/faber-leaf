## 1. Goal

Turn the layer rules from advisory warnings into a merge gate: zero violations,
`severity: error`, and no way to re-introduce the coupling P6–P8 just removed.

## 2. Why it is its own plan

A gate flipped while violations remain is a gate that gets reverted. A gate
flipped at zero is permanent. Separating "remove the coupling" (P6–P8) from
"forbid the coupling" (here) means the flip is a one-line change with a green
build behind it, which is the only version of this that survives review.

It also has to happen *before* W3. P15's exit criterion is that
`core-no-sculptcore` and `core-no-litemesh` "still hold at `error`" — they
cannot hold at `error` if they were never set to it.

## 3. Current state

- P1 repaired the rules and **published a real baseline** in its own document,
  with a per-rule breakdown. That table is this plan's input.
- P1 also added the `--max-warnings <n>` ratchet to `tools/check-layers.js`, so
  between P1 and here the count can only have gone down.
- Every rule is still `severity: warn`.

**Do not re-baseline from scratch.** The vacuous `288 warnings / 0 errors` the
pre-P1 config reported is not a number this plan may start from, and neither is
a fresh measurement that has not been reconciled against P1's table. Start from
P1's table, note what each intervening plan removed, and account for the
difference.

### Step 2 — drive the remainder to zero

Whatever survives is, by construction, the set nobody has looked at yet. Expect
three shapes:

- **Real leftovers** — a host file still importing an addon. Fix it the way P8
  did: registry lookup or delete.
- **Transitive-only hits** (`core-no-addons-transitive`, the `reachable: true`
  rule P1 added). These are the `core → tet → mesh` chains. Most disappear when
  `scripts/tet/` and `scripts/hair/` leave in P13 — but P13 is *after* this
  plan, so they need explicit handling now: see step 4.
- **Type-only hits** (`core-no-addons-typeonly`). These are Class A and P13
  removes them for free. They are counted separately precisely so they can be
  reasoned about separately.

### Step 3 — flip the severities

Set `severity: error` on:

- `core-no-mesh`, `util-no-mesh` (now targeting `^addons/builtin/mesh/`)
- `core-no-addons`, `core-no-addons-transitive`
- `core-no-view3d-tools`
- `core-no-litemesh`, `core-no-sculptcore` — these are at zero today and the
  entire point is that they must **never start** firing. Flipping them costs
  nothing now and is unaffordable later.

Leave at `warn` for now, with a dated note: `core-no-addons-typeonly` (P13
closes it) and `no-circular` (P17 owns it).

`tools/check-layers.js` exits non-zero on any `error`-severity hit, so this is
where the ratchet becomes a real gate. Keep `--max-warnings` pointed at the
remaining warn-rule count so those cannot grow either.

### Step 4 — exemptions are dated and owned, or they do not exist

Any rule that cannot be driven to zero gets an explicit entry in
`.dependency-cruiser.cjs` — a scoped `from`/`to` carve-out with a comment naming
**the plan that closes it and the date it is expected to close**. Never a silent
`severity: warn` on the whole rule, which is how the current config got into its
state.

Expected exemptions, both closing at P13:

- `scripts/tet/` and `scripts/hair/` → `addons/builtin/mesh/` (they *are* BREP
  consumers; they leave together).
- Whatever `core-no-addons-typeonly` still holds.

Two exemptions is a reasonable outcome. Ten is a sign step 2 was not finished.

### Step 5 — make the gate hard in CI

P1's `layers` job already runs. Confirm it is a **required** check on the
protected branch, not merely a job that runs. A red job that does not block is
the same as no job.

## 8. Departures from the plan as written

### 8a. `core-no-addons-transitive` stays at `warn` — P13 flips it

**The plan's step 3 and exit criteria both require this rule at `error`. It is not,
and could not be made so.**

The rule is `from: CORE, to: {path: '^addons/', reachable: true}` and reads 800.
Every surviving route runs through a file in the `BREP_CONSUMERS` set — the chains
are `core/context.ts → tet/tetgen.js → mesh/src/bvh.ts`,
`data_api/api_define.ts → hair/strand_ops.js → mesh/src/mesh.ts`, and
`editors/… → transform_ops.ts → mesh/src/mesh_base.ts`. Those are exactly the
intermediates step 4 sanctions exempting, and the exemption **cannot be expressed**:
dependency-cruiser 17.4.0 types a reachability `to` as `IReachabilityToRestrictionType`,
which extends `IBaseRestrictionType` and adds only `reachable` — so it accepts `path`,
`pathNot` and `reachable`, and nothing else. `via` / `viaOnly` belong to
`MiniDependencyRestrictionType` and are circular-dependency modifiers, not reachability
ones; `dependencyTypesNot` is rejected outright. Attempting either yields
`data/forbidden/N/to must NOT have additional properties … must match exactly one
schema in oneOf`. `pathNot` on the `to` does not help, because the exempted files are
*intermediates*, not endpoints.

Three options were considered and rejected:

1. **Post-filter the reach set in `tools/check-layers.js`.** Rejected: it reimplements
   depcruise's rule engine in our tooling, and a hand-rolled second engine is precisely
   the kind of thing that drifts from the config it claims to enforce.
2. **`options.exclude` the BREP-consumer files.** Rejected: it would drop them from
   `core-no-addons` too, hiding 13 real direct edges to fix one indirect count.
3. **Move `MeshTransType` / `InflateOp` / `ToSphereOp` / `InsetTransformOp` into the
   mesh addon now.** This is the only change that would genuinely zero the rule — but
   P13's deletion set already names `MeshTransType | 745 host lines,
   transform_types.ts:38-782`, so it is ~1000 lines of migration that P13 then deletes.
   Rejected as churn.

**Chosen:** the rule stays `warn` with its budget ratcheted 1152 → 800 and a comment in
`.dependency-cruiser.cjs` naming P13 as owner. When P13 deletes `scripts/tet/`,
`scripts/hair/` and the BREP transform stack, the intermediates vanish, the count goes
to zero on its own, and the flip becomes the one-line change this plan wanted it to be.
**P13's exit criteria must include flipping it.**

### 8b. A third exemption group, and it is a rule rather than a carve-out

Step 4 predicted two exemptions. There are three: `scripts/tet/` + `scripts/hair/` (as
predicted), whatever `core-no-addons-typeonly` still holds (as predicted), and the BREP
half of the transform stack — `transform_base.ts`, `transform_inset.ts`,
`transform_ops.ts`, `transform_types.ts` — which the plan did not anticipate because P1's
Class A list recorded them as type-only, and three of them turn out to carry a *runtime*
`MeshFlags` import as well.

They are BREP consumers on exactly the same footing as `scripts/tet/`: P13 deletes them,
and until then their `MeshFlags.SELECT` / `HIDE` / `UPDATE` / `MIRRORED` reads sit inside
`MeshTransType`, `InflateOp`, `ToSphereOp` and the inset code — all BREP-only paths. So
they join the same exemption group rather than getting one of their own.

The exemption is implemented as a **named rule with its own budget**
(`brep-consumers-no-addons`, 13) rather than a bare `from`/`to` carve-out on
`core-no-addons`. A carve-out would make the 13 edges invisible and let them grow freely;
a second rule keeps `core-no-addons` at `error`/0 while the exempted set stays ratcheted.
This is a stricter reading of step 4's "never a silent `severity: warn`", not a looser one.

### 8c. Step 5 (required CI check) needs a repo admin

The `layers` job runs and is wired into the PR merge gate. Whether it is a *required*
status check on the protected branch is a GitHub branch-protection setting, which cannot
be set from the working tree. **Flagged for the repo owner** — this is the last open item
on the plan's exit criteria.

### 8d. Two small gate fixes found on the way

  over.
- `tally()` seeded every rule's severity as `'warn'`, so a rule declared `error` that
