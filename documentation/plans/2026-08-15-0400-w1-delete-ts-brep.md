## 1. Goal

Delete `addons/builtin/mesh/` and everything that exists only to serve it —
63,839 lines of BREP plus its dependents (63,059 when this was written; P8 and
P10 moved work *into* the addon on the way here) — leaving a host that has never heard
of it.

By the time this plan runs, nothing in `scripts/` references the BREP (P8),
files without it round-trip (P10), and the tree has LeafMesh + a modeling
toolmode (P11, P12). This is a leaf delete. If it is not, an earlier plan is
unfinished and the correct action is to go back, not to push through.

**Archive, not port** — this settles decision #4. Each archived tree moves
intact under `archive/`, with a `README.md` saying what it was, what it depended
on, and which plan would port it. They are BREP subclasses (`curve.ts:75`,
`strand_types.js:36`), so porting means rewriting them against LeafMesh: a
feature project, not part of this refactor.

**Archiving the tet generator is the reason the disposition is not simply
"delete".** `scripts/tet/` is 3,875 lines of tetrahedral meshing, and like the
unwrapping stack it is expensive algorithm work that is lost by accident rather
than by decision. Subsurf, curves and hair come along because they are small,
because they are the three the strategy names, and because a half-populated
`archive/` invites the question of what else should have been in it.

The dev-addon harnesses are the counter-case and worth naming: they are *about*
the deleted features rather than being them, they are already broken against
P8's severed shim, and archiving them would preserve a test for something that
no longer exists.

### 2.1 Open decision #4 — curves, tets, hair, subsurf

**Settled: archive, do not port** — the recommendation this section carried,
taken as written. The reasoning is in §2's table.

Archiving is not free: `archive/` must be **excluded from the build, from
`tsconfig` includes, from `check:layers`, and from eslint**, or it becomes a
permanent source of noise that people fix instead of deleting. Set those
exclusions in the same commit.

Record the user-visible consequence: files containing curve, tet, hair or
subsurf data open through P10's unknown-addon path as preserved-but-inert
blocks. That is the designed behaviour and P10's tests assert it — this is the
first time it matters to a real user.

## 3. Rescue before delete

`unwrapping.ts`, `unwrapping_solve.ts`, `mesh_paramizer.ts` → `git mv` to
`archive/unwrapping/` **in a commit that lands before the delete commit**. P19
ports them onto `IUVSource`.

This is the single most expensive thing to lose in the whole refactor and it is
lost by accident, not by decision — a `git rm -r addons/builtin/mesh` takes it
with everything else. Make the rescue its own commit so it is visible in the
log and cannot be reverted along with the delete.

Same treatment for anything else the §2 table marks "archive": move first, in a
separate commit, then delete.

## 4. The manifest rewrite is not optional and not stageable

`scripts/addon/manifest.ts:164` **throws** on an unknown dependency, and
**every builtin addon except LeafMesh declares `"dependencies": ["mesh"]`** —
`curve`, `mesh_edit`, `subsurf`, `tetmesh`, and `sculptcore` itself. (`tetmesh`
was missing from this list and `pbvh_sculpt` was on it; P5 deleted the latter.
`leafmesh` declares `[]`, which P11 §4 made a point of.)

So the moment `mesh` stops existing, every remaining builtin fails to load. A
staged delete is impossible: **rewrite every builtin manifest in the same
change** as the delete.

Check, in this order:

1. Which addons are being deleted outright (their manifests go with them).
2. Which survive — at minimum `sculptcore` and `leafmesh` — and must drop the
   `"mesh"` dependency.
3. Whether the survivors actually *used* anything from mesh. If so, that usage
   is a P8 gap that leaked; fix it before deleting, not by re-adding the
   dependency.

Consider whether `manifest.ts:163-165` should throw at all. A missing dependency
that hard-fails the addon load is defensible; one that throws out of the addon
manager and takes the app with it is not. P14 owns the semantics — if the
behaviour needs to change, note it for P14 rather than changing it here.

### 10.6 Step 5 — the delete, and the two things it uncovered

`git rm -r` of §5's set: **72 files**. `pnpm gen:paths` then dropped

`npx tsgo --noEmit` then found **8 errors in 3 files** — the whole residue, and
both causes are the same mistake made twice: a *host* fact that had been living
inside the BREP.

- **`window._gl` was declared by the mesh addon.** `addons/builtin/mesh/src/mesh.ts`

- **`camera.ts` imported `CurveSpline` from the curve addon**, for the
  `SPLINE_PATH` camera that follows a curve block. This one broke at **step 2**,
  not step 5 — the rescue commit moved `addons/builtin/curve/` to `archive/curve/`
  and the dangling import went unnoticed because the tree has not typechecked
  since. The field is serialized (`curvespline: DataRef`), so deleting it would
  break P10's byte-identical round-trip. Instead the file now declares the shape
  it actually uses:

    length: number
    evaluate(t: number, tan: Vector3, nor: Vector3): Vector3
  }

  Nothing implements it any more, which is the honest state: a `SPLINE_PATH`
  camera in an old file keeps its `DataRef`, the block it points at loads as a
  preserved-but-inert `MissingDataBlock`, and the branch that would follow it
  never runs. This is the same host-owned-interface move P9 made for
  `view3d_utils` and `widget_tools`, and it is why `core-no-addons-typeonly`

### 10.9 Fallout — the widget-shape OBJ reader

`pnpm test` after the delete: **16 suites / 163 tests failed**, every one of them
`spawnSync nw.exe ETIMEDOUT`, and every one of them opaque, because a headless
NW.js run writes nothing to stdout (the renderer's fd is `EBADF`). Attaching to a
manual `--remote-debugging-port` boot and reading `Runtime.exceptionThrown` over
CDP produced the whole cause in one line:

```
Error: loadShapes called before setShapesObjLoader; ensure mesh addon registered
```

This is the same class of defect as §10.6's two, found a third time: **a host fact
that had been living inside the BREP.** `scripts/webgl/simplemesh_shapes.ts` owns
the widget gizmo meshes (`Shapes.ARROW`, `.SPHERE`, `.CURSOR`, …) that the
transform widgets and the 3D cursor draw — host code, in a host file, on the
startup path. But the OBJ parser that fills them was `addons/builtin/mesh/src/objloader.js`,
reached through a `setShapesObjLoader` hook the mesh addon called at registration.
The hook existed only to dodge a TDZ cycle: `framework_api.ts` re-exports
`Shapes`, and `mesh.ts` imports `@framework/api`. So the addon was, in effect, a
required part of app boot.

The host owns the parser now, split in two so it is testable:

| File | |
| --- | --- |
| `scripts/webgl/obj_parse.ts` | pure `parseOBJTris(buf) → {positions, normals}`; **imports nothing** |
| `scripts/webgl/simplemesh_obj.ts` | pours that into a `SimpleMesh` |

The split is forced by the test environment, and it follows existing precedent.
`tests/jest.config.ts` is jsdom + `@swc/jest`; importing `simplemesh` transitively
reaches `scripts/util/vectormath.js`, which `require`s an ESM and throws
`Must use import to load ES Module`. The leafmesh addon's own `obj_read.ts` is
laid out the same way for the same reason. `setShapesObjLoader` is deleted
outright rather than left dangling — with a host-local parser there is no cycle
to dodge, and nothing can ever call it again. `scripts/framework_api.ts` exports
just `Shapes`.

Behaviour is deliberately identical to the deleted BREP path, which was read out
of `git show 8788f6da^:addons/builtin/mesh/src/mesh_draw.ts` rather than guessed
at:

- **Flat shading.** `makeFace` never set `MeshFlags.SMOOTH_DRAW`, so every widget
  face was drawn with its own normal repeated at all three corners. Authored
  `vn`/`vt` lines were discarded then and are skipped now.
- **Fan triangulation** of n-gons, off vertex 0. Face normals by **Newell's
  method** — the shape files contain quads, for which a cross product of the
  first three corners is not the same answer.
- **Layers `LOC|NORMAL|UV|COLOR|ID`** — `LIT_MESH_VERTEX_LAYOUT` (`WidgetMeshShader`,
  `BasicLitMesh`, `NormalPassShader`) plus `MeshIDShader`'s id. The widget WGSL
  ignores the uv and color *values*, but the buffers must be bound, so they are
  seeded as `SimpleIsland._newElem` would have.

`tests/unit/obj_parse.test.ts` pins it: **23 tests**, two per shipped shape
(9 shapes × {whole triangles, finite coords, unit normals}) plus the format cases
that had no coverage at all before — n-gon fan output vertex-for-vertex, flat
normals, negative and `v/vt/vn` face refs, a degenerate `f 1 2 2` dropped rather
than emitted, and comment / `mtllib` / `usemtl` / `s off` lines ignored with CRLF
input. The `SimpleMesh` wiring stays uncovered here by necessity; the NW.js
integration suites cover it by booting the real app.

**Not a fallout, though it looks like one:** the integration log also carries
`Error: Cannot find module 'electron'` from `electron/[eval]`. That is
`sculptcore_fuzz.test.ts` probing for a resolvable Electron in order to *self-skip*,
which it has done since the NW.js migration deleted `electron/main.js`; the test
already carries an `XXX:` saying so. `electron/` is untracked and holds a stray
`node_modules` and a one-byte `arguments.txt`. Nothing to fix here — the suite is
correctly reporting that it cannot run.

### 10.10 The four suites the boot fix uncovered

With §10.9's fix in place the integration run went from **16 suites / 163 tests
failed** to 150 passed on the wasm leg and 163 on the native leg, leaving four
backend-agnostic suites red. Each was diagnosed separately; only one was a
regression this phase introduced.

| Suite | Cause | Fix |
| --- | --- | --- |
| `addon_set_settings_compat` (7) | **regression** — `JSZip is not defined` | side-effect import in `core/appstate.ts` |
| `file_compat` (1) | fixture addons default-on, over un-isolated app storage | `defaultEnabled: false` + `--app-storage-dir` |
| `legacy_file_compat` (3) | the contract flip the test itself predicted | assertions re-expressed as a transform |
| `addon_api_resolver` (1) | stale since **P11**, plus a half-covering build guard | assertion narrowed, guard widened |

**The JSZip global is the fourth instance of §10.6's class** — a host fact that
had been living inside the BREP. `scripts/core/appstate.ts` reads a bare `JSZip`
global in `createFile` / `loadFile` for compressed `.wproj`, and the only eager
loader of `scripts/extern/jszip/jszip.js` in the tree was
`addons/builtin/mesh/src/fbxloader.js:7`, a bare side-effect import. Deleting the
addon took the global with it and every save path threw. The consumer now imports
it itself. `tools/esbuilder.js` externals `'./scripts/extern/jszip/*'` and esbuild
rewrites a relative external against the *output* directory, so the bundle emits
`import "../scripts/extern/jszip/jszip.js"` from `build/` and resolves — verified
in `build/entry_point.js`, which now carries the static import alongside the
pre-existing dynamic one in the install path.

**`legacy_file_compat` was right to fail.** Its own header predicted this phase
would flip it: a `.wproj` whose objects point at `mesh` blocks now loads through
P10's preservation path, so `sceneobject.ts`'s `dataLink` hands back a
`NullObject` stub carrying the original `lib_id`/`lib_type`/`name`, and the file
reports one missing lib type rather than none. The fixture JSON was **not**
touched — it is the authoring record and the header says to assert against it,
never against re-derived values. Instead the test states the one thing this build
does differently, as a function:

```ts
function asThisBuildReportsIt(objects: LegacyMeta['objects']) {
  return objects.map((ob) => (ob.dataCls === BREP_DATA_CLS ? {...ob, dataCls: 'NullObject'} : ob))
}
```

Round-trip byte-identity still holds, which is the property P10 actually bought.

**`addon_api_resolver`'s negative assertion had been wrong since P11.**
`git log -S` puts `triangulateMesh` in `addons/builtin/leafmesh/src/api.ts` since
`67f1c6f3` (P11 step 1), so the generated stub legitimately names it and a bare
`not.toMatch(/triangulateMesh/)` could never pass. It went unnoticed because the
integration suites had been dead since step 5. The negatives now spot-check
*definitions* (`/function triangulateMesh/`, `/class LeafMeshData extends
SceneObjectData/`) rather than names, since the stub names every symbol `api.ts`
re-exports and a bare name proves nothing.

**`file_compat` had two causes stacked, and the second is the interesting one.**
`tools/build-addons.js --include-fixtures` runs in four suites' `beforeAll` and
writes `tests/fixtures/addons/*` into the same `build/addons/index.json` the app
fetches at boot (`addon.ts`'s `collectIndexSources`). `api_consumer` declares
`"dependencies": ["leafmesh"]` and had no `defaultEnabled`, so it defaulted to
*on* — and `file_compat`'s enable/disable cycle then got `has-dependents` on
steps 2 and 4. Dropping fixtures from the index is not available:
`addon_build.test.ts` asserts the index describes `test_addon`, `kind` and all.
Both fixture manifests now declare `"defaultEnabled": false`, which is the honest
statement — a test fixture is registered so a test can find it, and turned on by
the test that wants it, not by an app boot. No suite relied on the old behaviour;
all four read the artifacts off disk or import them directly.

That alone did not fix it, and the reason took a headless boot to see: **a
Chromium profile is not app state.** `file_compat`'s `boot()` passed
`isolatedProfileArgs()` (a fresh `--user-data-dir`) and nothing else, but
`settings.json` — including per-addon `enabled` flags — lives in
`<cwd>/.sculptcore` (`core/app_storage.ts`'s `buildStorage`), which a profile
directory does not isolate. So every boot inherited whichever addons the
*developer* last had enabled, and `settings._loadAddons()`'s pass 1 turned
`api_consumer` back on regardless of what its manifest said. A probe boot with a
fresh profile showed all four addons `enabled: true` with `defaultEnabled: false`
on three of them — which is the shape of the bug, exactly. `boot()` now passes
`--app-storage-dir` at a temp path, the flag that exists for this
(`documentation/native-electron-test-harness.md:79`). `addon_set_settings_compat`
and `sculptcore_autosave` were already doing it; the rest of the NW.js suites
still are not, which is worth a sweep but is not P13's.

The same shared state bites in the other direction: `addon_api_resolver`'s
`beforeAll` rebuilt only when `api_consumer/src/main.js` was missing, while one of
its tests asserts on `index.json` — and a plain `pnpm build` rewrites the index
*without* fixtures while leaving their bundles in place. The guard now checks both
artifacts.
