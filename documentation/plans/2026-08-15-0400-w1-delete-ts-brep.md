## 1. Goal

Delete `addons/builtin/mesh/` and everything that exists only to serve it —
63,839 lines of BREP plus its dependents (63,059 when this was written; P8 and
P10 moved work *into* the addon on the way here) — leaving a host that has never heard
of it.

By the time this plan runs, nothing in `scripts/` references the BREP (P8),
files without it round-trip (P10), and the tree has LeafMesh + a modeling
toolmode (P11, P12). This is a leaf delete. If it is not, an earlier plan is
unfinished and the correct action is to go back, not to push through.

## 2. Enumerate the regressions *before* deleting

§6 lists what goes away. Decide each one explicitly — **drop**, **port**, or
**preserve in `archive/`** — and record the decision in a table in this document
before a single file is removed. Deciding after the delete means deciding
without the code.

**Archive, not port** — this settles decision #4. Each archived tree moves
intact under `archive/`, with a `README.md` saying what it was, what it depended
on, and which plan would port it. They are BREP subclasses (`curve.ts:75`,
`strand_types.js:36`), so porting means rewriting them against LeafMesh: a
feature project, not part of this refactor.

**Archiving the tet generator is the reason the disposition is not simply
"delete".** `scripts/tet/` is 3,875 lines of tetrahedral meshing, and like the
unwrapping stack it is expensive algorithm work that is lost by accident rather
than by decision. Subsurf, curves and hair come along because they are small,
because they are the three the strategy names, and because a half-populated
`archive/` invites the question of what else should have been in it.

The dev-addon harnesses are the counter-case and worth naming: they are *about*
the deleted features rather than being them, they are already broken against
P8's severed shim, and archiving them would preserve a test for something that
no longer exists.

### 2.1 Open decision #4 — curves, tets, hair, subsurf

**Settled: archive, do not port** — the recommendation this section carried,
taken as written. The reasoning is in §2's table.

Archiving is not free: `archive/` must be **excluded from the build, from
`tsconfig` includes, from `check:layers`, and from eslint**, or it becomes a
permanent source of noise that people fix instead of deleting. Set those
exclusions in the same commit.

Record the user-visible consequence: files containing curve, tet, hair or
subsurf data open through P10's unknown-addon path as preserved-but-inert
blocks. That is the designed behaviour and P10's tests assert it — this is the
first time it matters to a real user.

## 3. Rescue before delete

`unwrapping.ts`, `unwrapping_solve.ts`, `mesh_paramizer.ts` → `git mv` to
`archive/unwrapping/` **in a commit that lands before the delete commit**. P19
ports them onto `IUVSource`.

This is the single most expensive thing to lose in the whole refactor and it is
lost by accident, not by decision — a `git rm -r addons/builtin/mesh` takes it
with everything else. Make the rescue its own commit so it is visible in the
log and cannot be reverted along with the delete.

Same treatment for anything else the §2 table marks "archive": move first, in a
separate commit, then delete.

## 4. The manifest rewrite is not optional and not stageable

`scripts/addon/manifest.ts:164` **throws** on an unknown dependency, and
**every builtin addon except LeafMesh declares `"dependencies": ["mesh"]`** —
`curve`, `mesh_edit`, `subsurf`, `tetmesh`, and `sculptcore` itself. (`tetmesh`
was missing from this list and `pbvh_sculpt` was on it; P5 deleted the latter.
`leafmesh` declares `[]`, which P11 §4 made a point of.)

So the moment `mesh` stops existing, every remaining builtin fails to load. A
staged delete is impossible: **rewrite every builtin manifest in the same
change** as the delete.

Check, in this order:

1. Which addons are being deleted outright (their manifests go with them).
2. Which survive — at minimum `sculptcore` and `leafmesh` — and must drop the
   `"mesh"` dependency.
3. Whether the survivors actually *used* anything from mesh. If so, that usage
   is a P8 gap that leaked; fix it before deleting, not by re-adding the
   dependency.

Consider whether `manifest.ts:163-165` should throw at all. A missing dependency
that hard-fails the addon load is defensible; one that throws out of the addon
manager and takes the app with it is not. P14 owns the semantics — if the
behaviour needs to change, note it for P14 rather than changing it here.

## 8. Risks

- **The unwrapping stack is deleted by accident.** Mitigation: §3's separate,
  earlier rescue commit.
- **A survivor actually needed the mesh addon.** Mitigation: §4 step 3 — find it
  before the delete, fix it in P8's style.
- **The packaging test is lost.** Mitigation: §6 step 3, before the delete.
- **Review burden — ~63k deleted lines.** Mitigation: by construction the
  imports are already gone (P8), so the delete PR is near-mechanical. Review
  effort should go to §4's manifest rewrite and §6 step 6's rule changes, which

  behaviour, but it must be *communicated*: the app should say which addon is
  missing, by name, from the file. P10's `missing_addon` work should already do
  this — verify it does, on a real BREP file, before shipping.
